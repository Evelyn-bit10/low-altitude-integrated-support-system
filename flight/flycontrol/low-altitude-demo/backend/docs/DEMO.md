# 功能演示台使用说明

> 一页三屏，点一下就跑：**① 进出场程序　② 多设备去重　③ 对外数据推送**
> 入口：`http://127.0.0.1:5500/demo.html`

---

## 1. 一键启动

双击项目根目录的 **`启动演示.bat`**。

它会自动完成：

| 步骤 | 服务 | 端口 | 说明 |
| --- | --- | --- | --- |
| 1 | flycontrol 后端 | 8080 | 以 `PUSH_MODE=http` 启动（推送走真实 HTTP） |
| 2 | 模拟 UOM 接收端 | 8099 | 校验签名并落盘，供第三幕演示 |
| 3 | 门户静态服务 | 5500 | 承载演示台页面 |
| 4 | 打开浏览器 | — | 自动打开 `demo.html` |

已在运行的服务会自动复用。

> 如果本机 venv 不可用（指向不存在的 `C:\Python314`），脚本会退回系统 `python`；
> 仍失败时先按 `README.md` 重建 `backend\.venv`。

## 2. 演示脚本（约 5 分钟）

### 第一幕：进出场程序（90 秒）

**操作**：在「进出场方向」区点 **NE**，再点「生成进场」。

**讲解词**：

> 系统支持 8 个进出场方向。选方向后，它先去**方案库**取该方向的标准程序；
> 如果这条程序过不了障碍物或限飞区校验，会**自动**改用 A\* + Dubins 动态重规划。

**看哪里**：

- 左上角红/橙/绿标签：`方案库直出` / `动态重规划` / `不可用`；
- 右侧「生成结果」：标准程序名、来源、航路点数、合规与仿真结论；
- 地图：绿色实线是进场航路，橙色虚线是复飞段，红圈是障碍物。

**加分演示**：

- 点 **NW** → 提示「不可用」，原因是侵入临时限飞区（地图上紫色虚线框）；
- 点「全部 8 方向」→ 一次生成 8 条，地图上 8 个方向同时亮起。

---

### 第二幕：多设备去重（90 秒）

**操作**：切到「② 多设备去重」，点 **开始上报**。

**讲解词**：

> 两台设备（A、B）各自看到 5 架飞机，一帧共上报 **10 条**。
> 服务端判断是否为同一架：**先看 ua_id、再看实名登记号、最后才用时空门限**；
> 其中一架在 B 侧丢了 ID，靠位置匹配找回来的。
> 输出只剩 **7 条**，其中 3 条标了「双源」——它们被两个设备同时看到，但只输出一次。

**看哪里**：

- 顶部四个数字：`原始上报 10 → 去重后 7 / 融合 3 / 待确认 0`；
- **俯视图**（重点）：
  - 蓝点 = A 设备看到的，紫点 = B 设备看到的（同一架在两台设备上的坐标略有偏差）；
  - 两点之间的**灰色虚线和「≡」** = 这两条观测被判定为同一架；
  - **绿色圆环** = 去重后保留下来的唯一航迹，下方的 UA-xxxx 是它的编号；
  - 圆环会**偏向蓝点一侧**：A 设备 σ=10、B 设备 σ=30，融合按 1/σ² 加权，更信任准的那个；
  - 只有单个蓝点/紫点的，说明只有一台设备看到；
  - 右上角可以取消勾选「显示 A/B 原始观测」，只看融合结果；
- 「合并明细」表：左边 A 设备编号、右边 B 设备编号，最后一列是判定依据（ua_id / 时空门限）；
- 「唯一航迹」表：3 条带「双源」标签。

**加分演示**：

- 点「发一组"不同飞机"」→ 两架 ua_id 不同、相距 19 m，**仍然输出 2 条**，
  证明不是"靠得近就合并"。
- 点「停止」后等 15 秒，航迹自动过期消失（TTL）。

---

### 第三幕：对外数据推送（90 秒）

**操作**：切到「③ 对外数据推送」。

**讲解词**：

> 态势、飞行程序、气象会按需推送到政府平台/UOM。
> 每条报文带 **msgId**（幂等）和 **HMAC-SHA256 签名**；
> 先写**发件箱**再发送，断网不丢，失败按指数退避重试。

**看哪里**：

- 左上四个指标：发送成功 / 待发送 / 成功率 / 平均延迟；
- 右侧「模拟对端收到的报文」：类型、msgId、条数、**签名校验结果**；
- 状态灯：`模拟 UOM 8099` 应为绿色。

**加分演示**：

- 点「发送测试报文」→ 右侧立刻出现一条 `HEARTBEAT`，签名 `OK`；
- 点「立即推送队列」→ 把积压的消息一次发完，失败数应为 0。

> 如果右侧列表为空：说明后端不是 `PUSH_MODE=http` 启动的（左上会显示 `dry-run`）。
> 用「启动演示.bat」启动即可；手动启动时设环境变量 `PUSH_MODE=http`。

## 去重页的合并动画

第二幕「多设备去重」的俯视图上有一层动效，用来把"合并"这件事**画出来**：

| 效果 | 触发时机 | 含义 |
| --- | --- | --- |
| 飞线 + 拖尾 | 航迹新增了来源（新合并） | 这条观测被并入某条唯一航迹 |
| 汇聚流 | 每帧挑 1 条双源航迹（轮播） | 多源观测持续汇聚到同一条航迹 |
| 脉冲环 | 飞线抵达时 | 合并完成 |
| 雷达扫描 | 常驻，6 秒一圈 | 纯装饰，营造"在持续监视"的感觉 |

实现要点（`demo.html`）：

- 对比相邻两帧的 `source_ids`，发现"某个航迹多了一个来源"就触发；
- 动效参数偏克制：每帧 1 条、时长 0.7~0.85 秒、光晕半径 7px、拖尾透明度 0.32；
- **光点每帧重算起终点**：只记录"从哪个观测点到哪条航迹"，绘制时用插值后的
  实时坐标，所以光点始终追着移动中的飞机（早期版本存的是静态像素坐标，
  飞机走了光点还在原地，看起来"跟不上"）；
- 位置用当前帧的坐标变换（`px/py`）换算，保证与底图对齐；
- 动画直接画在同一张画布上（叠加层 canvas 在部分浏览器会被当成不透明白块）；
- 有动画时以 60fps 重绘整张图，无动画时保持每秒一次的轮询重绘。

## 第四幕「RL 影子模式」

第四幕是一块**对比屏**，回答一个问题：*策略到底比规则好在哪？*

```
┌──────────────────────────────────────┬──────────────────────────────┐
│ 错配 1 ← 规则 103   │ 漏配 0 ← 规则 4  │  柱状图：4 个场景的错配数对比 │
│ 碎片 1.92 ← 2.25    │ 奖励 499 ← -345  │                              │
├──────────────────────────────────────┴──────────────────────────────┤
│ 结论条：困难密集 错配 103 → 1（降 99%），稀疏场景两者接近              │
├─────────────────────────────────────────────────────────────────────┤
│ 场景 × 做法 明细表（奖励/错配/漏配/碎片/被拆）                        │
├─────────────────────────────────────────────────────────────────────┤
│ 实时影子流（帧/来源/规则→/策略→/p/一致）                              │
└─────────────────────────────────────────────────────────────────────┘
```

### 数据从哪来

点「跑密集场景对比」→ `GET /api/rl/compare/all`：

- 用**带真值**的仿真场景（`experiments/dedup_ml/sim.py`）跑四遍：
  稀疏 / 密集 / 困难密集 / 蜂群；
- 规则和 PPO 各跑一遍**同一批数据**，统计真实的对错；
- 首次约 15 秒，之后走内存缓存。

和影子模式的区别：

| | 影子模式 | 场景对比 |
| --- | --- | --- |
| 数据 | 实时流 / 回放 | 带真值的仿真 |
| 能回答 | 两边**是否一致** | 谁**更对**（错配/漏配） |
| 用途 | 上线前验证 | 讲清价值 |

### 实测结论（30 帧）

| 场景 | 规则 错配/漏配/碎片 | PPO 错配/漏配/碎片 |
| --- | --- | --- |
| 稀疏空域 | 0 / 10 / 2.67 | 0 / 4 / 2.17 |
| 密集空域 | 4 / 14 / 2.75 | 6 / 8 / 2.25 |
| **困难密集** | **103 / 4 / 2.25** | **1 / 0 / 1.92** |
| 蜂群 40×40m | 545 / 0 / 1.92 | 537 / 0 / 1.92 |

- **困难密集**是价值所在：规则在门限附近反复误并，错配 103 → 1；
- **蜂群**两者都做不好（12 架挤在 40 m 内，物理上不可分辨），
  差距只有 8 —— 诚实地说，这个场景任何策略都救不了；
- **稀疏**策略略保守（漏配更少、碎片更少），没有退化成"乱合并"。


### 画面稳定性（踩过的坑）

**第一版**：点位每秒"跳"一次（只做了插值，没改机位）。
**第二版**：加了相机缓动，结果更糟——相机追着匀速平移的目标跑，
看起来像整张图在晃，而且"飞机不动"（相机跟着走，相对位移被抵消）。

根因：`min/max` 包围盒随飞机移动变化 → 中心和缩放跟着变。

**最终方案：固定机位**。世界范围由每架的盘旋包络**一次性算出**，
之后永不变化；飞机在这个固定框里各自绕圈（`r`/`w`/`ph` 三个参数），
画面里每个点都在移动，而机位一丝不动。

现在做了三件事：

| 问题 | 处理 |
| --- | --- |
| 整张图抖动 | **固定机位**：世界范围只算一次（盘旋包络），之后不变 |
| 飞机"不动" | 每架按 `r/w/ph` 各自盘旋，朝向沿切线实时变化 |
| 点位每秒跳一次 | 相邻两帧之间做**位置插值**（900ms easeInOut），60fps 平滑移动 |
| 数据静默时画面不动 | 第二幕可见时以 60fps 重绘，雷达扫描持续旋转 |

插值只影响画面，不参与任何判定（`feedInterp` 只写绘制用的 `_x/_y`）。

### 融合环位置：改成前端实时算

早期融合环直接用服务端返回的 `lat/lon`，实测会出现"环比观测点跑得快"：
同一段时间里 A-1 移动 5 m、环移动 22 m（`gap` 从 12.5 漂到 26.2），
根因是服务端融合坐标受"本帧处理了哪些观测"影响，帧间会小跳。

现在改成**前端按当前 A/B 观测点做 1/σ² 加权**：

```js
const fusedXY = (t) => {                       // σ: A=12, B=16
  let sx = 0, sy = 0, sw = 0;
  Object.keys(t.source_ids).forEach(src => {
    const p = pointsD.find(q => q.src === src && q.id === t.source_ids[src]);
    const w = 1 / (src === 'A-RID' ? 12 : 16) ** 2;
    sx += p.x * w; sy += p.y * w; sw += w;
  });
  return [sx / sw, sy / sw];
};
```

环和观测点用**同一帧、同一插值**，所以永远同步、绝不滞后，而且融合点稳定落在
A、B 之间偏 A 的位置（权重 64:36）。

## 第一幕：航迹的方向标注

俯视图上加了三种标注，让"哪条是进场、往哪个方向飞"一眼可见：

| 元素 | 样式 | 说明 |
| --- | --- | --- |
| **方向箭头** | 白色 chevron + 深色描边，沿航迹等距 5 个 | 箭头指向飞行方向；白色是为了在任何航迹颜色上都看得清 |
| **进场 / 离场** | 带底色的小标签，放在航迹 10% 处 | 由 `program.type` 决定，不会压到旁边的文字 |
| **复飞段** | 橙色虚线 + 橙色箭头 + `复飞` 标签 | 离场程序的该段标为「复飞·返场」（避免和进场复飞混淆） |

实现要点：

- `drawDirArrows()` 先按屏幕坐标算累计弧长，再等分取点，用 `atan2` 求切向；
  注意 `py` 是翻转的，所以角度必须用**屏幕坐标**算，不能用世界坐标；
- 箭头加 1.4 px 深色描边，否则浅色航迹上完全看不见（第一版就踩了这个坑）；
- 复飞标签取航段 35% 处，原来放在起点会压在"起降点"上。

## 页面初始化失效的排查记录（v1.8）

### 现象

改完 UI 后页面「看起来正常」——按钮渲染、状态灯亮、布局完好——但：

* URL 参数 `?tab=p2` / `?dir=NW` / `?gen=arrival` 全部失效；
* 定时器（推荐历史、影子流）不刷新；
* 控制台**没有报错**。

### 根因

```js
$('#btn-rec').onclick = ...     // 这个按钮在 HTML 里不存在
```

这是一行 **top-level** 代码。JS 在顶层抛错后，**文件里后面所有代码都不执行**——
包括 URL 参数处理、`setInterval` 注册、初始化 IIFE。而按钮渲染、状态灯这些都在抛错之前，
所以页面"半死"，极易误判为网络或后端问题。

### 修复

1. 补上按钮 HTML；
2. 所有 top-level 的元素绑定改为防御写法：`if ($('#x')) $('#x').onclick = ...`；
3. **把静态检查并进冒烟测试**：扫描 JS 里所有 `$('#xxx')` 引用，比对 HTML 是否存在该 id。

冒烟测试现在输出：

```
[静态检查] JS 引用的元素 id
  [OK]   demo.html      引用完整
  [OK]   rl_lab.html    引用完整
...
7/7 通过（含 2 项静态检查）
```

验证有效性：故意把 `id="pval"` 改成 `id="pval_x"`，检查立刻报出 `缺失 id: ['pval']`。

### 教训

「页面能渲染」≠「JS 跑通了」。冒烟测试最初只检查"截图存在 + 无 Uncaught 关键字"，
抓不到这类**静默中断**；静态 id 比对是成本最低、命中率最高的一道防线。

```
  → 前端再校验一遍接续段是否穿障碍（ENU 换算，40 m 采样），穿则沿航迹换点
  → 飞机出现在点击处，虚线连到航道入口
点「开始飞行」
  → 按落地顺序分配时隙（先到先得，间隔 45 模型秒）
  → 前机未拉开 600 m：后机在入口等待（粉字）
  → 已进航道但时隙未到：按"剩余路程 ÷ 剩余时间"配速慢飞（黄字）
  → 时隙到：加速 2.3× 落地（绿字）
  → 落地：航迹变灰，2 秒后整条移除
```

### 已知限制（演示级近似，非产品实现）

1. 前后机间距用"距跑道距离差"近似，实测最小约 303 m（目标 320 m），来自每帧离散步进
2. 两条**不同方向**的航道在跑道口汇合时不做几何校验，只靠"同一时刻只有一架在保护圈内"
3. 接续段是"直线 + 沿航迹换点"，不做 A* 绕飞

### 接口补充

| 字段 | 含义 |
