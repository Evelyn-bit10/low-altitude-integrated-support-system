# 多设备态势去重（同一性判定）

> 需求：同一架无人机可能被多个设备/节点同时看到，下游只能输出**一条**记录。
> 实现：`app/services/dedup.py`（算法） + `app/routers/traffic.py`（接入）。

---

## 1. 数据流

```
  A 设备 ─┐
          ├─► POST /api/traffic/ingest ─► 归一化 ─► DedupEngine ─► TrafficStore
  B 设备 ─┘        (数组/单对象/信封)         (补 ts/来源/质量)   (同一性判定)    │
                                                                              ├─► GET /api/traffic
                                                                              ├─► GET /api/sync/snapshot
                                                                              └─► GET /api/traffic/stats
```

去重**只在服务端做一次**，门户、App、快照、后续的 UOM 推送全部复用同一份结果。

---

## 2. 判定规则（三档证据 + 一票否决）

| 档位 | 依据 | 结论 |
| --- | --- | --- |
| 强正 | `ua_id` 相同 | 同一架（1.0） |
| 强正 | `reg_no` 相同 | 同一架（0.95） |
| **强负** | 双方都有 `ua_id` 但不同 | **一定不是同一架**，几何再近也不合并 |
| 弱 | 距离 ≤ `v_max·Δt + 3σ`、高差 ≤ 30 m、航向差 ≤ 30° | 疑似同一架（≤0.9） |
| 中性 | 一方无 ID | 匹配后继承对方身份（有条件，见下） |

补充规则：

- **身份继承有前置条件**：同一来源 / 该航迹上一帧仍在跟踪 / 失联后位置几乎重合（≤ σ）。
  防止"没有 ID 的无人机飞到某架失联飞机的旧位置附近，就把人家的身份继承走"。
- **未确认不输出**：无 ID 的新航迹先处于 `TENTATIVE`，连续 2 帧命中才转 `CONFIRMED`；
  带 ID 的航迹创建即确认。避免单帧异常报文在界面上闪出一条"幽灵"。
- **同源连续性接管**：同一设备偶发一条异常数据（航向跳变/GPS 抖动）时，用放宽 1.5 倍的门限
  继续跟原航迹，而不是新建。
- **生命周期**：15 秒无更新删除；两个源连续 3 帧分歧超过 `3.44·√(σ_a²+σ_b²)` 才拆回两条
  （固定阈值会把"噪声差异"误判成两个目标）。
- **门限按统计推导**：`gate = 3.44 · √(σ_obs² + σ_track² + (v_max·Δt)²/3)`，
  3.44 对应 χ²(2, 99.7%)；σ 可从报文携带，或按 `source_node` 查表，且有下限 8 m 防止低估。
- **时间对齐**：每个源维护「收到时刻 − 报文时刻」的滑动均值，校正后再算 Δt，
  避免设备时钟偏差把门限放大/缩小（1 s 偏差实测会造成约 5 倍漏配）。
- **全局分配**：一帧内先收集所有候选边，再按分数从高到低统一分配，
  而不是"逐条挑最近"（后者在密集场景容易被先处理的观测抢走候选）。
- **空间网格**：目标数 > 200 时启用网格索引（格 ≈111 m，失联航迹单独线性补扫）。

## 3. 接口

### 3.1 上报

```http
POST /api/traffic/ingest
Content-Type: application/json

[
  {"id":"7A21","source_node":"A-RID","ts":"2026-10-22T10:00:00Z",
   "lat":30.0,"lon":120.0,"alt_msl":120,"speed":12,"heading":45,
   "ua_id":"1581F...","reg_no":"UA-12H7K9Q3","phase":"CRUISE"}
]
```

`ts` / `source_node` / `quality` 缺省时由服务端补齐（`shared/interface.py` 的
`normalize_traffic_record`），老客户端不改也能用。

### 3.2 查询（已去重）

```http
GET /api/traffic
```

返回的每条记录包含 `global_id`、`sources`、`source_ids`、`confidence`、`merged`、
`callsign`（主源呼号，供界面展示），`id` 为 `ua_id` / `reg_no` / `global_id`。

### 3.3 统计（门户面板用）

```http
GET /api/traffic/stats
```

```json
{"enabled":true,"node_id":"NODE-A","input":10,"unique":7,"merged":3,
 "tentative":0,"duplicate":0,"created":7,"matched":3,"expired":0,"split":0,
 "sources":[{"source":"A-RID","tracks":5},{"source":"B-RID","tracks":5}],
 "unique_now":7,"merged_now":3}
```

| 变量 | 默认 | 说明 |

| `DEDUP_CALIB_SAMPLES` | `200` | 累计多少对样本后更新一次 |

## 7. 已知边界

| 项 | 现状 | 影响 |
| --- | --- | --- |
| 匹配为贪心，非全局最优 | 密集编队/交叉场景可能错配 | 建议后续换 Hungarian / JPDA |
| 门限用欧氏距离，未用预测位置 | 门限部分被位移吃掉 | 可改为「先预测再门限」的马氏距离 |
| 匹配复杂度 O(目标数 × 观测数) | 500 目标约 44 ms/帧 | 超 500 架需加空间网格索引 |
| 无持久化 | 进程重启 `global_id` 变化 | 生产需落库 `lp_traffic` |
| 无合并审计 | 无法回溯"为什么合并" | 建议增加 `cluster_assoc` 表 |
| 时钟不统一时门限失真 | 跨设备需对时 | 建议 NTP 或在心跳里估计偏移 |
| 跨设备交接会新建一条 | 旧航迹保留 15 s，短暂重复 | 安全优先的取舍，可调 `_absorbable` |

## 8. 改进记录（v1.1）

### 8.1 改了什么

| # | 改动 | 位置 |
| --- | --- | --- |
| 1 | **门限按统计推导**：`gate = 3.44·√(σ_obs² + σ_track² + (v_max·Δt)²/3)`，替换原来的 `v_max·Δt + 3σ` | `_gate()` |
| 2 | **σ 成为一等参数**：报文可带 `sigma`，否则按源查表；带下限 8 m 防低估 | `Observation.sigma` / `sigma_of()` |
| 3 | **每源时钟对齐**：用「收到时刻 − 报文时刻」的滑动均值估计偏移并校正 ts | `sync_time()` |
| 4 | **全局边分配**：一帧内先收集全部候选边，再按分数统一分配（原来逐条贪心） | `ingest()` ③ |
| 5 | **空间网格索引**：>200 目标时启用（格 ≈111 m，失联航迹单独补扫） | `_rebuild_grid()` |
| 6 | **拆分阈值按 σ 推导**：`3.44·√(σ_a²+σ_b²)`，避免把噪声差异当成两个目标 | `_check_split()` |
| 7 | **融合改逆方差加权**：`w = 1/σ²`（原来用 quality） | `_refresh()` |
| 8 | 告警报文接入推送（`ALERT`） | `push_service.collect()` |

### 8.2 实测对比（仿真，真值 12 架）

| 500 架 | 527.5 条 / 76.0 ms | **500.4 条** / **30.5 ms** |

复现：`python experiments/dedup_ml/bench_compare.py`

### 8.3 为什么这几项有效

- **漏配的真正来源是固定门限**：噪声一放大，`v_max·Δt + 45 m` 就不够用了；改成按 σ 和 Δt 缩放后，同一架不再被拆开。
- **时钟偏差比想象中致命**：设备时钟快 3 秒时，`Δt` 被压成 0，门限塌缩到 45 m，输出从 12 条涨到 29 条。
- **拆分阈值也是固定值**：A/B 噪声差 3 倍时，正常偏差就有 60~70 m，固定 67.5 m 会把同一架拆成两条 —— 这是"越融合越多"的隐藏原因。
- **全局分配**在密集场景避免"先处理的观测抢走候选"。

## v1.3 · 事后回并与最优指派

### 1. 航迹级事后回并（默认开启）

**问题**：在线分配是"一帧一帧决策"。某帧因为门限抖动/时钟偏差没配上，就会新建一条
碎片航迹；之后两边各自延续，再也不会合到一起。实测 12 架飞机输出 12.9~13.8 条。

**做法**：每帧末尾做一次回并扫描（`DedupEngine._post_merge`），条件**宁可不合**：

| 约束 | 取值 | 作用 |
| --- | --- | --- |
| 身份 | ua_id / reg_no 相同或双方都没有 | 防止把不同飞机合成一条 |
| 成熟度 | 双方 hits ≥ merge_frames | 避免刚建的噪声航迹被吸走 |
| 时效 | 双方都在最近 1 秒更新过 | 只合"同时在线的" |
| 距离 | d ≤ 1.2 × max(σ_a, σ_b) | 碎片应该几乎重合 |
| 朝向 | 航向差 ≤ 30°（低速豁免） | 交叉飞行的两架不能合 |
| **互为最近邻** | a 的最近邻是 b，且 b 的最近邻是 a | 防止链式合并 |
| **密度保护** | 第三近航迹 > 3σ | 蜂群场景空间分辨不了，直接放弃 |

来源可能重叠（一条被拆成两条各自双源），合并时按 `ts` 保留更新的那条观测。

**实测（12 架，60 帧，真值已知）**：

| 场景 | 贪心 | 贪心 + 回并 | 误配变化 |
| --- | --- | --- | --- |
| 稀疏（无 ID） | 12.9 条 / 误 1 | **12.0 条 / 误 1** | 不变 |
| 密集（无 ID） | 13.8 条 / 误 2 | **12.0 条 / 误 2** | 不变 |
| 困难密集 | 12.0 条 / 误 2 | 12.0 条 / 误 2 | 不变 |
| 蜂群 40×40m | 11.8 条 / 误 12 | 11.8 条 / 误 12 | 不变（密度保护生效） |

> 稀疏/密集场景**输出条数正好等于真值 12**，且没有增加任何误配。

### 2. 最优指派（可选，默认关闭）

`app/services/assignment.py` 实现了 O(n³) 匈牙利算法（纯标准库，已用暴力法随机校验 300 组）。

```python
DedupEngine(assign_mode="hungarian")     # 或环境变量 DEDUP_ASSIGN=hungarian
```

按来源分组求解（"同源对同一航迹只能一次"恰好是标准二分匹配）。**实测暂无增益**：
在这些场景里贪心已经是最优或接近最优，所以默认仍是 `greedy`，只在密集场景需要时可切换。

## v1.4 · 匀速模型卡尔曼滤波（预测与门限）

### 为什么改

原来的门限是**圆**、靠三个手工 σ 合成：

```python
gate = 3.44 * sqrt(s_obs² + s_trk² + s_motion²)
```

三个缺陷：

| 缺陷 | 后果 |
| --- | --- |
| 门限各向同性 | 沿航向和垂直航向一样宽 —— 交叉飞行的两架容易被吞 |
| 不确定度不随 Δt 正确增长 | 久未更新的目标门限偏小 → 误并 |
| 直接信报文里的 speed / heading | 设备不报或报错时，外推直接崩 |

### 怎么改

每条航迹挂一个**匀速（CV）卡尔曼滤波器**（`app/services/kalman.py`，纯 Python 4 状态）：

```
状态 x = [px, py, vx, vy]（局部 ENU 米），协方差 P 为 4×4
预测：x' = Fx,  P' = FPFᵀ + Q(σ_a, Δt)      ← Q 用白噪声加速度模型
更新：K = P'Hᵀ(HP'Hᵀ+R)⁻¹（Joseph 形式保证正定）
门限：σ_eff = sqrt(νᵀSν / νᵀν)  →  gate = 3.44 · σ_eff
```

- `3.44 = √χ²(2, 99.7%)`，与原来的统计含义**完全一致**，行为平滑迁移；
- 每个源用自己的 σ 作为 R（复用现有的 σ 自标定结果）；
- 帧首对每条航迹**只预测一次**，本帧所有候选边共用（`_predict` 变成只读）。

### 数值验证

用 numpy 写了一份独立参考实现，逐帧对比 500 帧：

```
最大偏差 2.27e-13（位置/速度/协方差全部对比）
```

### 融合也搬进滤波器（v1.4b）

第一版里位置仍由"逆方差加权"算，滤波器只是"跟随"。第二版把**逐源观测直接喂进滤波器**：

```
每个源用自己的 σ 作为观测噪声 R  → 等价于信息量加权，而且顺带估出速度
异步到达的旧观测（超出同步窗口）→ 只更新身份，不更新状态
_refresh 一帧内可能被调多次    → 用 kf_applied 记录已应用的 ts，同一观测只进一次
速度/航向优先用滤波估计（报文里的 speed/heading 经常缺失或跳变）
```

### 效果（12 架 × 60 帧，带真值，事后回并同时开启）

| 场景 | 关卡尔曼 | 开卡尔曼 | 误配变化 |
| --- | --- | --- | --- |
| 稀疏（无 ID） | 12.0 条 / 1 | 12.2 条 / 1 | 不变 |
| 密集（无 ID） | 12.0 条 / 2 | **11.9 条 / 2** | 不变 |
| 困难密集 | 12.0 条 / 2 | 12.0 条 / 2 | 不变 |
| 蜂群 40×40m | 11.8 条 / 12 | 11.8 条 / 12 | 不变 |

单帧耗时 0.9 → 1.3 ms（仍在 5 ms 预算内）。

**诚实结论**：合成场景上基本持平（稀疏略降 0.2 条、密集略升 0.1 条、误配一条没变）。
收益不在这些数字上，而在：

* 速度/航向不再依赖报文（真实设备经常不报或跳变）；
* 多源融合按信息量加权，且顺带给出速度状态；
* 不确定度随 Δt 正确增长，门限不用再手工调。

**参数扫过**：σ_a = 1/2/3/4/6 全试过，2 最稳（3 以上困难密集误配从 2 涨到 4），默认 2.0。

**一个反直觉的坑**：建轨时如果把首条观测标记为"已应用"（避免重复计数），
稀疏场景会从 12.2 恶化到 12.9、误配从 2 涨到 3 —— 因为滤波器少了一次校正，
初始噪声位置一直没被修正。**宁可轻微重复计数，也不要跳过首次更新。**

> 说明：合成场景里源噪声各向同性，椭圆的优势不明显；真正体现价值的是**真实数据的抖动、丢包和时延**。
> 另外，事后回并也用了滤波后的位置来判断"两条碎片是否重合"，两者是配合关系。

## v1.5 · 性能优化与两个实测结论

### 性能：500 架 69 ms → 36 ms（-48%）

用 cProfile 定位后做了三处改动：

| 问题 | 处理 |
| --- | --- |
| 网格只按"格子"粗筛，格子里的航迹全做完整打分（15.7 万次 `_geo_score`） | 打分前先用**真实距离**过滤，调用量降到 2.7 万次 |
| `distance_m` 里每度经线长度算了 58 万次 | 按 0.001° 量化后缓存 |
| `_refresh` 一帧内被调 1.5 万次（分配后/合并后/帧尾） | 观测集合没变就短路（标定采样单独去重，见下） |

| 规模 | 优化前 | 优化后 |
| --- | --- | --- |
| 12 架 | 0.95 ms | 0.61 ms |
| 100 架 | 12.15 ms | 9.07 ms |
| 200 架 | 36.42 ms | 29.36 ms |
| 500 架 | 68.74 ms | **36.01 ms** |

> 踩坑：给 `_refresh` 加短路后，**σ 自标定被饿死**（`sigma_scale` 一直停在 1.0），
> 单测抓到了。把标定采样提到短路之前、并按 `(帧, 最新时刻)` 去重才正确——
> 不去重又会重复累计，实测把影子一致率从 96% 打到 81%。

### 结论 1：密度自适应门限**没有收益**（默认关闭）

实现：按最近邻航迹距离把门限缩放到 0.6~1.0 倍（最近邻 >250 m 不缩放）。

4 个 seed 平均：

| 场景 | 关 | 开 |
| --- | --- | --- |
| 稀疏 | 11.96 / 误 1.00 | 11.96 / 误 1.00 |
| 密集 | 11.98 / 误 3.25 | 12.16 / 误 3.50 |
| 困难密集 | 11.98 / 误 5.25 | 11.98 / 误 5.25 |
| 蜂群 | 11.83 / 误 12.00 | 11.82 / 误 12.25 |

单 seed 时曾看到"困难密集 误配 4→3"，扩到 4 个 seed 后消失——**是噪声**。
默认关闭，需要时 `DEDUP_DENSITY_GATE=1`。

### 结论 2：特征 `已跟踪帧数` 是频率相关的（已修）

原特征用的是 `t.hits`（按**观测条数**累加）：10 Hz 时一条航迹 12 秒就有 118 个 hits，
而训练回合只有 40 帧 → 严重出分布，策略在高频源上会大面积拒判。

**已改成时间量** `航迹存活时长/60 = min(now - first_seen, 60) / 60`，对上报频率不变，
并重新训练（阈值也随之标定为 0.80）。

修完在**干净进程**里测（重要，见下面的坑）：

| 上报间隔 | 影子一致率 |
| --- | --- |
| 1.0 s | 100.0% |
| 0.25 s | 100.0% |
| 0.1 s | 98.7% |
